# Системные требования к модулю-оркестратору

1. **Приём заявок.** Оркестратор должен принимать заявки на ручной и регламентный запуск процессов оценки рисков с указанием расчётной даты и необходимых источников данных.

2. **Управление очередью.** Если необходимые ресурсы заняты, задача должна помещаться в очередь и ожидать возможности запуска.

3. **Предотвращение конфликтов.** Оркестратор не должен допускать одновременное выполнение процессов, использующих одни и те же эксклюзивные источники данных.

4. **Предотвращение взаимных блокировок.** Перед запуском задачи все необходимые ей ресурсы должны выделяться одновременно. Если хотя бы один ресурс недоступен, задача остаётся в очереди.

5. **Проверка дубликатов.** Система должна отклонять повторные заявки на выполнение одного процесса за одну расчётную дату, если такой расчёт уже выполняется или ожидает запуска.

6. **Параллельное выполнение.** Процессы, не использующие общие ресурсы, должны иметь возможность выполняться одновременно.

7. **Управление приоритетами.** Оркестратор должен определять порядок запуска задач с учётом типа запуска, ожидаемой продолжительности и времени ожидания.

8. **Автоматическое освобождение ресурсов.** После завершения задачи или возникновения ошибки занятые ресурсы должны освобождаться, а очередь — пересматриваться.

9. **Контроль состояния задач.** Система должна отслеживать статусы задач: «В очереди», «Выполняется», «Завершено», «Ошибка», «Отклонено».

10. **История выполнения.** Оркестратор должен сохранять информацию о поступлении, начале и завершении задач для последующего анализа.

11. **Обработка одновременных заявок.** Система должна корректно обрабатывать несколько заявок, поступающих одновременно, без нарушения правил использования ресурсов.

12. **Пользовательский интерфейс.** Система должна предоставлять возможность добавления задач, просмотра очереди, активных процессов и результатов выполнения.

| 3 | `get_busy_resources()`, атомарный старт, сценарии S1/S2/S5 | Реализовано в одном экземпляре |
| 4 | `schedule()`, `test_s4_no_deadlock_atomic_reservation` | Реализовано в модели эксклюзивных ресурсов |
| 5 | `find_duplicate()`, `test_s3_reject_duplicate`, сценарий S3 | Реализовано; тест дубликата именно в очереди рекомендован отдельно |
| 6 | `test_s1_parallel_independent_processes`, сценарий S2 | Реализовано |

| 12 | `ui/app.py` в открытом PR #4 | Интерфейс предложен, **не включён** в ветку `dev-5`; очереди разных Streamlit-сессий изолированы |

Автоматические тесты в репозитории: `tests/test_orchestrator.py` (7 тестов). Дополнительные проверки и интеграция интерфейса выполняются отдельно. Сценарии S1–S5 демонстрируются через `python -m src.run_scenarios`; их поле `expected` сейчас выводится текстом и не превращается в подробные автоматические утверждения.

**Область применимости:** синтетический журнал и модельное время. Нулевая конкуренция за общие ресурсы внутри симуляции не означает устранения всех причин сбоев реальных расчётов.
